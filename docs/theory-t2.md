# T2 · Конвейер «эксперимент → артефакт → страница»

## Исследовательский вопрос

Где заканчивается вычислительный эксперимент и начинается публикация?
Сравниваются способы, при которых результат расчёта попадает на страницу, а не сами генераторы сайтов.
Критерии: воспроизводимость, контроль устаревания, параметризация, стоимость CI и удобство отладки.

## Сравнительная матрица

| Способ | Исполнение и зависимости | Кэш / обнаружение изменений | Параметры и связь с данными | Применимость |
| --- | --- | --- | --- | --- |
| Изображения вручную | Расчёт вне сборки, PNG/SVG добавляют вручную | Нет автоматической инвалидации; картинку легко забыть обновить | Нужен отдельный manifest | Быстрый базовый вариант и тяжёлые эксперименты, если публикация контролируется отдельно |
| nbconvert | ExecutePreprocessor запускает ядро Jupyter; затем экспортирует notebook | Сам по себе не полноценный кэш зависимостей; внешнюю оркестрацию нужно добавить | Параметры через код/обёртку, входные файлы явно фиксируются | Линейные небольшие ноутбуки и существующие .ipynb |
| MyST-NB | Исполнение ноутбуков интегрировано со Sphinx | `nb_execution_mode="cache"`, jupyter-cache; изменение внешнего CSV нужно учитывать отдельно | Богатые ссылки и научный текст, но нужен явный учёт внешних входов | Исследовательская документация и книги на Sphinx |
| Quarto | `quarto render` исполняет через Jupyter/knitr/другой движок | `cache` и `freeze` — разные механизмы; `freeze:auto` отслеживает исходный документ, не произвольный внешний файл | Параметры проекта/документа, многовыходная публикация | Отчёты HTML/PDF и проекты с несколькими языками |
| papermill | Исполняет .ipynb, подставляя значения в ячейку с тегом parameters | Не заменяет граф зависимостей; кэш запусков строится отдельно | Удобная параметризация и отдельный выходной notebook на запуск | Серии экспериментов; публикацию результатов организует следующий шаг |
| Скрипт + Makefile | Явный `make experiment` перед MkDocs; Python может читать CSV без Jupyter | Собственный ключ по данным, коду, окружению; результаты хранятся отдельно | Все параметры и версии можно включить в manifest | Небольшой командный проект, простая отладка и низкая стоимость CI |

Свойства исполнения nbconvert, MyST-NB, Quarto и papermill сверены с официальной документацией:
[nbconvert](https://nbconvert.readthedocs.io/en/latest/execute_api.html),
[MyST-NB](https://myst-nb.readthedocs.io/en/latest/computation/execute.html),
[Quarto](https://quarto.org/docs/projects/code-execution.html),
[papermill](https://papermill.readthedocs.io/en/latest/usage-parameterize.html).
Эти инструменты в данной работе **не запускались для сравнительного бенчмарка**; матрица описывает механизмы, а не измеренные скорости.

## Цена воспроизводимости

**Изображение — артефакт, но не описание эксперимента.** Вручную сохранённый график не объясняет, из какого файла и каким кодом он получен.
Исполняемый notebook улучшает наблюдаемость, однако скрытое состояние ядра и зависимость от порядка ячеек могут ухудшить воспроизводимость.
Решение — исполнение с чистым ядром и явными входами; для скрипта — отсутствие неявного глобального состояния.

Кэш должен включать не только текст notebook/скрипта, но и внешние данные.
В Quarto `freeze` управляет повторным выполнением при глобальном render; отдельный render документа всё равно исполняет его.
Изменение CSV вне документа может требовать `--cache-refresh` или удаления устаревшего freeze.
Нельзя считать автоматически, что «есть cache» означает «отслеживаются все зависимости».

## Ограничения CI

| Ресурс | Ограничение / модель | Следствие для эксперимента |
| --- | --- | --- |
| Длительность job | GitHub-hosted: до 6 часов на job; локально в workflow выставлено 15 минут | Тяжёлые запуски переносятся за пределы публикации; бессрочное ожидание недопустимо |
| Минуты | Для GitHub Free в таблице тарифов указано 2 000 минут/месяц; стандартные hosted runners публичных репозиториев имеют отдельную модель бесплатного использования | Не переносить квоты приватного репозитория на публичный без проверки тарифа |
| GPU | Обычный `ubuntu-24.04` CPU-runner в этом проекте не предоставляет GPU | Обучение GPU-моделей на этом job не выполняется; нужен иной runner/кластер |
| Хранилище артефактов | В таблице GitHub Free указано 500 MB; квота и тарификация зависят от плана/публичности | Не упаковывать весь архив в артефакт сайта, хранить только нужные результаты |
| Кэш | Базовый лимит в таблице — 10 GB на репозиторий; возможны вытеснение и ограничения политики | Кэш — ускорение, а не единственное долговременное хранилище результата |
| Размер публикации | Pages и S3/SSH-хостинг имеют собственные ограничения сверх Actions storage | Большие веса моделей и исходные датасеты выносить из каталога сайта |
| Сеть и секреты | Внешний сервис может быть недоступен; PR из fork не получает обычные deploy-секреты | Сборка должна читать уже зафиксированный срез; deploy отделяется от непроверенного кода |

Числа в таблице — ограничения из [официальной документации GitHub](https://docs.github.com/en/actions/reference/limits), а не замеры проекта.
Лимиты изменяемы; перед длительными запусками нужно проверить актуальный план.
О бесплатном использовании стандартных runner в публичных репозиториях см.
[GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions).
Проект намеренно не делает утверждение «GPU вообще нет в GitHub»: существуют другие классы runner.

## Граница стратегий

### Вычисления выполняются в CI

Подходит, если расчёт детерминирован, входные данные доступны без интерактивной авторизации, нет GPU,
а время и память с запасом помещаются в budget job. Для данного CSV расчёт короткий, поэтому CI выполняет его непосредственно.
Сайт не должен зависеть от ранее запущенной вручную локальной команды.

```text
commit → validate CSV → compute/cache → CSV + JSON + HTML figure → strict build → artifact → deploy
```

### Вычисления отдельно, CI только публикует

Подходит при многочасовом обучении, платных API, GPU, больших или закрытых данных, нестабильных внешних сервисах.
Вычислительная система один раз сохраняет проверенный артефакт и manifest, а публикация проверяет хеши и строит страницы.
Отказ сайта не должен запускать многосуточное обучение повторно.

| Поле manifest | Назначение |
| --- | --- |
| run_id и время UTC | Однозначный запуск |
| git_commit и признак dirty | Точный код; нельзя выдавать рабочее дерево с правками за чистый коммит |
| data_version и SHA-256 | Снимок данных, а не только имя CSV |
| dependency_lock_sha256 / image digest | Окружение расчёта |
| parameters и random_seed | Условия запуска |
| outputs: имя, SHA-256, размер | Проверяемые артефакты |
| schema_version и статус проверки | Совместимость с генератором сайта |

Рекомендуемый порядок: compute → проверка метрик → загрузка неизменяемых артефактов по run_id → manifest → публикация ссылки на этот manifest.
CI проверяет существование и хеши, а не доверяет изменяемой ссылке `latest.csv`.
Для персональных/закрытых данных публикуются только допустимые агрегаты.

## Вывод для данной предметной области

Рекомендуется **Python-скрипт + Makefile + MkDocs Material**, потому что сезонные показатели считаются быстро,
входной CSV мал, а читаемый diff Markdown/CSV и простой кэш важнее notebook-интерфейса.
Это не вывод сравнительного T1 о превосходстве MkDocs над всеми SSG.

Рекомендация меняется при необходимости встроенного исполнения и сложных научных cross-reference (MyST-NB/Sphinx),
одновременного HTML/PDF и нескольких языков вычислений (Quarto),
больших параметрических серий notebook (papermill как вычислительный этап),
или тяжёлых GPU-экспериментов (внешний compute + подписанный/хешированный manifest + лёгкий CI публикации).
